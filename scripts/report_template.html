Image Search Engine: search photos by text or by example

Type a description or upload a picture and get back the most similar images from a collection. Built on CLIP-style embeddings and an exact nearest-neighbour index, and, more importantly, measured: five embedding models compared on two labelled benchmarks.

Role — solo design & build Stack — Python, open_clip, FAISS, FastAPI, Streamlit Data — COCO val2017 (5,000 images), Oxford-IIIT Pets (7,389 images)

Objective

Build a search engine over an image collection that works two ways: text → image ("a red double decker bus") and image → image (upload a photo, find look-alikes). Both use one index and one similarity measure.

Anyone can wire a model to a search box and show a demo. The goal here was to also answer the question a demo can't: how good is the search, actually? That means a labelled test set, standard retrieval metrics, and a fair comparison between models, so that every claim in this report comes with a number.

How it works, in plain terms

The whole system rests on one idea: a CLIP-style model can turn both pictures and sentences into lists of numbers (vectors) such that a picture and a sentence that mean the same thing end up with nearly the same numbers. Once everything lives in that shared space, "search" becomes "find the closest vectors".

  1. Embed every image once. The image encoder turns each photo into one vector. This is the slow step (minutes), and it happens offline.
  2. Store the vectors in an index. FAISS keeps them in memory and can find the nearest ones to any query vector almost instantly.
  3. Embed the query the same way. A text query goes through the text encoder; an uploaded image goes through the image encoder. Both produce a vector in the same space.
  4. Return the closest images. "Closest" means highest cosine similarity: the angle between two vectors is small when the content matches. The top k are shown ranked by score.

One space, two query types

There is no separate "caption matching" step. A sentence and a photo are both just vectors, so the same index answers both kinds of query.

Exact search, on purpose

With a few thousand images, brute-force comparison takes milliseconds and returns the true nearest neighbours. Approximate indices only pay off at millions of images, and they would add error to the evaluation.

Vectors are normalised

Every vector is scaled to length 1, so the inner product FAISS computes is exactly cosine similarity. Scores are comparable across queries.

Models are swappable

The model is just a name and a weights tag (for example ViT-L-16-SigLIP-256 + webli). Each model gets its own index, which is what made a five-model comparison cheap to run.

The app

A FastAPI service loads the model and index once and exposes /search/text and /search/image; a Streamlit page sits on top of it with a text tab, an image-upload tab, a dataset selector and a results slider. Each result shows its similarity score.

How the search is evaluated

"It returned plausible pictures" is not a result. Two labelled benchmarks turn search quality into numbers, one per query type.

Text → image: COCO val2017

5,000 images, each with about five human-written captions: {{n_queries}} caption queries in total. For each caption, the one correct answer is the image it was written for. No manual labelling was needed.

Image → image: Oxford Pets

7,389 photos of 37 cat and dog breeds (about 200 per breed). Every photo is used as a query against all the others, and a result counts as correct if it is the same breed. The query itself is excluded.

The metrics, without the jargon

Recall@k

How often the correct image shows up somewhere in the top k results. Recall@1 = "was it the very first result?"; recall@10 = "was it on the first page?".

MRR

Mean reciprocal rank. If the correct image is at rank 1 you score 1, at rank 2 you score ½, at rank 4 you score ¼; then average. Higher means the right answer sits nearer the top.

Precision@k

Of the top k results, what fraction were correct (same breed). 0.92 at k=10 means about 9 of 10 results were the right breed.

mAP

Mean average precision. Rewards putting all the same-breed images near the top of the full ranking, not just the first few. The strictest single number for Pets.

Two metrics are deliberately left out of the headline tables: precision@10 on COCO is capped at 0.1 (only one image is "correct"), and recall@k on Pets is capped near 5% at k=10 (about 200 correct images per query). Both are uninformative in those settings.

Finding 4 — the strict metric understates real quality. "A big bowl with some food inside of it" is matched by many bowls, and the benchmark only accepts one. Across all queries, the correct image is first {{top1_hit}} of the time, but of the {{n_miss}} cases where it isn't, the image returned instead shares at least one COCO object category with the expected one {{miss_cat}} of the time. Two random COCO images do so only {{rand_cat}} of the time, and the average category overlap (Jaccard) is {{miss_jac}} versus {{rand_jac}} for random pairs.

Read this carefully. Sharing a category is a coarse check ("person" appears in many images), so this does not prove that every miss is acceptable. It shows that the misses are overwhelmingly near-misses, not random failures. Human relevance judgements would be needed for a precise estimate.

Engineering notes

Leave-one-out for image queries

An indexed image always finds itself at rank 1 with similarity 1.0 (visible in the screenshot above). The evaluation removes the query from its own results; otherwise every image-to-image score would be inflated.

One command per model

Building an index and running the whole evaluation is two commands, and each run writes a JSON file under results/. The tables and charts in this report are generated from those files by script, with no hand-copied numbers.

Small hardware, deliberate choices

Everything ran on a laptop GTX 1060 (6 GB). That pinned PyTorch to CUDA 12.6 builds (newer ones drop this GPU generation) and Python to 3.12. Building an index took about 2–3 minutes for the smallest model and over ten minutes per dataset for the largest.

Safe image serving

The API only serves filenames that exist in the index, which blocks path-traversal requests, and validates k, the dataset name and uploaded files before doing any work.

Limitations & what's next

  • Possible training-data overlap. The models are pretrained on web-scale data (LAION-2B, WebLI) that may contain COCO or Pets images. These numbers show how well this pipeline retrieves with these models, not performance on guaranteed-unseen data.
  • One correct image per caption. COCO often has several images that fit a caption equally well. Finding 4 quantifies the effect only coarsely; proper human relevance judgements were not collected.
  • Pets relevance is breed-only. Two different breeds that look alike count as a miss.
  • Small, curated datasets. 5,000 and 7,389 images. Latency and index scaling at millions of images were not tested; exact search would give way to an approximate index there.
  • Latency is from one laptop GPU and is meant for comparing models with each other, not as a production figure.
  • Evaluation covers the embedding models, not the API or UI. There is no load test, and the app is a single-user local demo.
  • Next steps: a personal-photo collection as a demo set; image-only baselines (DINOv2) for Pets; a caption-then-embed baseline using a vision-language model; query rewriting or re-ranking on top of the top-k; an error analysis with human judgements.
